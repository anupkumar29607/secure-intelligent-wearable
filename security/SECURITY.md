# 1. Security Requirements

## SR-01 — API Input Validation
All API requests must validate input data before processing.

## SR-02 — Server-Generated Incident ID
Incident IDs must be generated by the backend server and must not be trusted from client input.

## SR-03 — Server-Generated Timestamp
Incident timestamps must be generated by the backend server.

## SR-04 — Encryption Key Protection
Encryption keys must never be exposed through API responses, frontend code, logs, or public repositories.

## SR-05 — Evidence Storage
Evidence such as images or videos must not be stored directly on the blockchain.

Evidence should follow:

Evidence → Encryption → Off-chain Storage → SHA-256 Hash → Blockchain Record

## SR-06 — GPS Validation
Latitude and longitude values must be validated before being stored or processed.

Valid ranges:
- Latitude: -90 to 90
- Longitude: -180 to 180

## SR-07 — Unauthorized Modification Protection
Only authorized operations should be allowed to acknowledge, modify, or resolve an incident.

## SR-08 — Evidence Integrity Verification
Evidence integrity must be verified using its SHA-256 hash before declaring that the evidence matches the recorded integrity reference.

## SR-09 — Minimal Data Exposure
The system should expose only the personal and incident information required by the responder dashboard.

## SR-10 — Simulation Transparency
Simulated sensor, GPS, AI, and hardware data must be clearly identified as simulated data.

# 3. Security Principles

1. Validate all external input.
2. Never trust client-generated identifiers or timestamps.
3. Protect encryption keys.
4. Do not store sensitive evidence directly on blockchain.
5. Use cryptographic hashing to verify evidence integrity.
6. Minimize exposure of personal information.
7. Clearly distinguish simulated data from real sensor data.
8. Do not mark a security test as PASS until it has actually been executed.
